# 第13章 効果・許可・外部領域

## 宣言と実行許可

効果は、関数が行う操作をsignatureの一部にする仕組みです。`effects {output}`を宣言しても、あらゆる環境で自動的に操作を許可されるわけではありません。実行者の許可も必要です。

| 効果 | 主な用途 |
|---|---|
| input / output | 標準入力、stdout / stderr |
| fileRead / fileWrite | root内の仮想file操作 |
| args / env | 引数、許可された環境変数 |
| locale / random | locale、VM乱数 |
| clock | 時刻の観測 |
| tasks | task、channel、scheduler |
| gui | ネイティブ画面とGUI入力 |
| external | 即時の外部操作領域 |
| network | HTTP、TCP、listener |
| db | SQLite、PostgreSQL |
| live | journalを作らない外部操作 |

単一sourceの既定許可はinput、output、args、locale、random、tasksです。file、env、clock、gui、external、network、db、liveが必要なら明示します。Envは環境変数名の許可も必要です。

~~~sh
rewind run main.rw --allow-effects fileRead,fileWrite
rewind run main.rw --allow-effects gui
rewind run main.rw --allow-effects external,network,tasks
rewind run main.rw --allow-effects external,db,tasks
~~~

効果不足の診断では、呼出し元のeffectsとCLIの許可を両方確認します。効果検査は通信先URLの妥当性やSQLの正しさを保証するものではありません。

## externalの境界

File.writeTextやOut.printlnはpublishを待つ仮想I/Oです。通信やDBはVM外の相手とやり取りするため、external領域を使います。領域の終了はpublishではありません。

~~~syntax
var pending:Option<Task<Result<HttpResponse,HttpError>>>=None;
external {
    pending=Some(http.get(url,10000,65536));
}
// 領域の外でTaskを待つ
~~~

領域内では操作をsubmitします。await、task切替、checkpoint、publish、領域を抜ける制御フローは拒否されます。Taskを作ったら外へ出てawaitする二段階の形にしてください。Taskの生成後にpublishしても、まだ完了していない通信が完了扱いになることはありません。

## 通常・fresh・live

通常のexternalは観測結果を保持し、同じcheckpointに戻った場合に再利用します。external freshは新しい操作として扱います。どちらも、実際に起きた外部作用をrevertで消しません。

external liveはreplay用の外部journalを作りません。明示的なlive許可が必要です。記録を残さないから高速・安全・再現可能だと一括して考えないでください。replayに必要な観測を失う境界であり、通常領域とは保証が異なります。

## Secret

Secretは診断や記録で値を伏せるための型です。暗号化、メモリ上の完全消去、誤送信防止をすべて自動保証する型ではありません。HTTP credentialやDB credentialsのalias登録では、値をfingerprintに直接入れないためのopaque参照と組み合わせます。

公開ログに接続文字列やtokenを自分でprintlnすれば、Secretを使う設計の意図を壊します。権限、ログ、記録の共有範囲をアプリケーション側でも決めてください。

# 第14章 コンソール入力と引数

## 引数を読む

アプリ引数はCLIの`--`より後ろへ渡します。手前はREWINDのオプションです。

~~~rewind arguments
let arguments=Args.all();
Out.println(arguments.len());
if arguments.len()>0 {Out.println(arguments.get(0));}
publish;
~~~

~~~sh
rewind run main.rw -- sample
~~~

この場合は1、sampleを出力します。`-- --help`もapplication引数であり、REWINDのヘルプを開く指定ではありません。引数の数を先に検査し、getの範囲外診断を利用説明の代わりにしないようにします。

## byte scannerを使う

大量の空白区切り整数を読む場合、Stringを全部splitするとtokenごとの中間値が増えます。std.scannerはBytesを保持して位置を進めるparserです。次の例は入力を固定して、その挙動を確認しています。

~~~rewind scanner
import std.scanner as scanner;
fn take<T,E>(value:Result<T,E>)->T effects {} {
    match move value {Ok(v)=>{return move v;},Err(_)=>{panic("parse failed");}}
}
let input=Bytes("10 -3 7\n");
let scan=take(scanner.fromBytes(input));
assert_eq(scanner.nextInt(&mut scan),Ok(Some(10)));
assert_eq(scanner.nextInt(&mut scan),Ok(Some(-3)));
assert_eq(scanner.nextInt(&mut scan),Ok(Some(7)));
assert_eq(scanner.nextInt(&mut scan),Ok(None));
~~~

EOFはOk(None)です。InvalidNumberとOverflowは失敗です。fromBytesの入力容量は1MiBです。空白はASCII spaceと9〜13で、任意のUnicode空白を認識するscannerではありません。失敗前にcursorが進む場合があるため、Errだから自動で入力位置が元に戻るとは考えないでください。

## 増分入力・出力

std.streamはtoken、UTF-8、writerの補助を提供します。In.readChunkとOut.writeBytesを組み合わせれば、全部を一つのStringへ集めることを避けられます。chunkの境目でUTF-8文字やtokenが分割されるため、状態を保持するdecoder/parserを使います。

一度のpublishに巨大な出力を集めることもメモリを使います。適切な単位で確定する設計にするとpending領域を抑えられますが、後のrevertでその公開済み出力を取り消せなくなる点も考慮してください。

## 整数入力の実用設計

「必要数だけ読めた」「各値が許容範囲」「余分なtokenの扱い」を決めてください。入力が途中で終わったらNoneを正常値として加算せず、不足として扱います。空入力を許すか、空配列を返すか、利用説明を出すかはプログラムの仕様です。

# 第15章 Fileとpublishの失敗

## 書込みはまずVMへ

~~~rewind files
File.writeText("state.txt","saved");
publish;
assert_eq(File.readText("state.txt"),Ok("saved"));
~~~

実行にはfileReadとfileWriteを許可します。この例は実行root内にstate.txtを書きます。writeTextしただけでは外部へ確定しません。commit/revertの対象となるpending操作をpublishで反映します。

Fileのsource内パスは相対パス、`/`区切りです。絶対パス、`..`、drive指定、root外へのsymlinkを許可しません。rootは単に見やすい表示名ではなく、アクセスの基準です。rootの外へ保存したいから相対パスに`../`を付ける使い方は拒否されます。

## 読取りと観測

readTextはResultを返します。ファイルがないこと、読み出せないこと、内容が期待と違うことを区別して処理します。読み取りは外部観測でもあるため、replayでは記録を使って検証できます。replayが無断でHost fileを上書きすることは通常ありません。

入力ファイルを読み、検査し、新しい内容を準備して、最後にpublishする形は扱いやすい設計です。保存直前に外部から変更された場合はExternalStateConflictになることがあります。勝手に上書きして解決するのではなく、利用者へ競合を伝える設計を考えます。

## 複数操作は一括atomicではない

複数file、directory、stdout、GUIを一つのpublishに含めても、OS全体のtransactionになる保証はありません。適用途中で失敗するとPublishPartiallyAppliedが返り、成功確認済みの操作と失敗phaseを調べる必要があります。

「エラーだから何も起きていない」と判断すると、既に保存したfileや表示した出力を二重に適用する可能性があります。同じruntimeで盲目的な再publishは拒否されます。実際の外部状態と診断のappliedを確認し、再開の方法を判断してください。

DB transactionとの違いにも注意します。FileのpublishはDBのcommitではなく、DBのcommitはVMのcheckpoint作成ではありません。

## cleanup

FileHandleにはusingがあり、scope終了時の解放を表現できます。接続やcursorにもscope所有と明示closeがあります。cleanup中の失敗も無視せず、元の診断へcausesとして追加される情報を調べてください。scopeを抜けたことと、外部書込みがpublishされたことも別です。

# 第16章 文字列・Unicode・正規表現

## 一文字の単位を選ぶ

| 操作 | index・長さの単位 |
|---|---|
| String.byteLen、String.find | UTF-8 byte |
| String.charLen、std.text.length | Unicode scalar |
| String.utf16Len | UTF-16 code unit |
| String.slice | byte半開区間、UTF-8境界を検査 |
| std.text.slice / find | scalar区間 / scalar offset |
| std.unicode.grapheme* | extended grapheme cluster |
| regex span、unicode offsets | UTF-8 byte offset |

~~~rewind text
import std.text as text;
assert_eq("a😀界".byteLen(),8);
assert_eq("a😀界".charLen(),3);
assert_eq("a😀界".utf16Len(),4);
assert_eq(text.slice("a😀界",1,3),Ok("😀界"));
assert_eq("a😀界".slice(1,5),Ok("😀"));
~~~

byte、scalar、graphemeを混ぜると、日本語や絵文字で不具合が出ます。regexのspanをstd.text.sliceへそのまま渡すことも間違いになり得ます。単位を関数の名前やデータ型の説明へ残してください。

## graphemeと正規化

見た目一文字の「e＋結合アクセント」は二つのscalarで一つのgraphemeになり得ます。国旗や家族の絵文字も同様です。GUIのbackspaceを人が見た一文字単位にしたいならgrapheme編集を選びます。

~~~rewind unicode
import std.unicode as unicode;
fn take<T,E>(value:Result<T,E>)->T effects {} {
    match move value {Ok(v)=>{return move v;},Err(_)=>{panic("unicode failed");}}
}
let source="é🇯🇵👩‍👩‍👧‍👦";
assert_eq(take(unicode.graphemeCount(&source)),3);
assert_eq(take(unicode.graphemeSlice(&source,1,2)),"🇯🇵");
let normalized=take(unicode.normalize(&source,unicode.Form::NFC));
assert_eq(take(unicode.isNormalized(&normalized,unicode.Form::NFC)),true);
let clusters=take(unicode.graphemes(&source));
clusters.add("!");
assert_eq(clusters.len(),4);
~~~

StringやMapキーを自動正規化する規則はありません。NFC/NFD/NFKC/NFKDを明示して使います。互換正規化は見た目や意味に影響する文字も変えるため、ユーザーが入力した原文を無条件にNFKCへ書き換えるべきかは用途で判断します。データ版はunicode.versionsで確認できます。

## 正規表現

std.regexでcompileしたRegexを再利用します。findは見つからなければNoneを返し、spanはbyte区間です。groupはそのcaptureが参加しなければNoneになる場合があります。続きの検索にはAPIのcursorを使います。

対応する文法はAPI契約に従います。すべての他言語のregex拡張と同じとは限りません。特に任意のbackreferenceやlookaroundを前提にせず、compile結果を検査してください。regex自体と入力にも容量・work予算があります。

## 正規化と検索の順番

正規化後のStringで得たoffsetを元のStringへ戻して使うと、byte列が変わっているため間違います。原文を表示する検索では、正規化後の結果と原文の対応を別途管理するか、どの文字列のoffsetかを明確にしてください。
