## 第23章 実行予算と性能

### 予算がある理由

REWIND のプログラムには、実行の量に上限があります。巻き戻しや再生のために、実行の履歴を保持する言語では、無限ループや暴走した処理が、環境のメモリやディスクを使い切ってしまうと、後始末が困難になるからです。上限を超えると、実行は止まり、どの予算が尽きたかが診断に出ます。

### 予算の種類

| 予算 | 指定 | 既定値 | 尽きたときの診断 |
|---|---|---|---|
| 実行ステップ（全体の累計） | `--steps N` | 1,000,000 | `ExecutionBudgetExceeded` |
| ネイティブ処理量（全体の累計） | `--native-work N`、`runtime { nativeWork = N; }` | 1,000,000（GUI の権限があるときは 256,000,000） | `NativeWorkBudgetExceeded` |
| 1 タスクあたりのステップ | `--task-steps N` | 100,000 | `TaskBudgetExceeded` |
| 履歴メモリ | `--history-memory SIZE` | 512 MiB | `HistoryMemory` |
| 履歴ストレージ | `--history-storage SIZE` | 8 GiB | `HistoryStorage` |
| 履歴の退避しきい値 | `--spill-threshold SIZE` | 8 MiB | （超えた分をストレージへ退避する） |

- **ステップ** は、プログラムが実行した命令の数です。
- **ネイティブ処理量** は、標準ライブラリがネイティブコードで行う処理（配列の演算、文字列の処理、`freeze` のコピーなど）の見積もりです。API ごとに、費用が文書に書かれています。
- **履歴** は、チェックポイントが保持しているデータです。

これらは **論理的な仕事量** の上限で、CPU 時間やメモリ使用量そのものではありません。どのマシンで動かしても、同じプログラムは同じ量を消費します。

### 既定の予算は小さい

既定の実行ステップは 100 万です。これは、思ったよりずっと小さい値です。たとえば、10 万回の足し算を繰り返すだけで、予算を使い切ってしまいます。

```rewind-error ExecutionBudgetExceeded
fn main()->Int {
    var total = 0;
    for i in 0..100000 { total += i; }
    Out.println(total);
    return 0;
}
```

1 回の反復で、約 10 個の命令が実行されるからです。意図した計算なら、実行するときに予算を引き上げます。

```sh
rewind run main.rw --steps 10000000
```

同じプログラムを、予算を引き上げて実行すれば、最後まで動きます。

```rewind steps=10000000
fn main()->Int {
    var total = 0;
    for i in 0..100000 { total += i; }
    Out.println(total);
    return 0;
}
```

```text
4999950000
```

エラーのヒントにある通り、予算を引き上げるのは、**仕事の量が意図したものである** と確かめた後にしてください。止まらないループを、予算を引き上げてごまかしても、解決にはなりません。

### 予算は巻き戻らない

予算は **累計** です。`revert` や `resume` で状態を戻しても、使った分は戻りません。そのため、巻き戻しを繰り返すプログラムも、いつかは止まります。第11章の「終わらない `resume`」が、止まるのも同じ理由です。

### ソースの中で指定する

`runtime { 設定 = 値; }` をソースに書くと、プログラムの中から予算を指定できます。設定名は `executionSteps`、`nativeWork`、`historyMemory`、`historyStorage`、`spillThreshold` で、サイズには `KB`、`MB`、`GB`（`KiB`、`MiB`、`GiB`）を付けられます。

```rewind-error ExecutionBudgetExceeded
runtime { executionSteps = 1000; }

fn main()->Int {
    var i = 0;
    while i < 100000 { i += 1; }
    return 0;
}
```

`nativeWork` と `executionSteps` は、実行する側が `--native-work` や `--steps` で上限を指定しているとき、それより小さくすることだけができます。すでに使った分を、ソースの設定や `revert` で回復することはできません。

### 呼び出しの深さと、そのほかの制限

関数の呼び出しの深さにも上限があり、再帰が約 1,000 段を超えると、`ExecutionBudgetExceeded`（call depth）で止まります。

| 項目 | 上限 |
|---|---|
| ソースファイル | 1 MiB / module、module は 256 個まで |
| 構文の入れ子 | 64 段 |
| `freeze` の深さ | 64 段（循環や資源を含む値は不可） |

Linux では、コンパイラと実行時に、アドレス空間の上限（既定 2 GiB）が掛かり、`--memory-mib` で変えられます。Windows には、この OS の上限がないため、`--memory-mib` を指定するとエラーになります。論理的な予算は、どちらの OS でも有効です。OS がプロセスを強制終了したときは、`Result` として回復することはできません。

### 重いと感じたら

1. `rewind profile --profile-format text` で、どの関数・どの行に仕事が集中しているかを調べます（第22章）。
2. ループで数値を一つずつ処理しているなら、数値配列（第21章）で、まとめて処理できないか考えます。ネイティブコードで実行されるため、同じ仕事を、ずっと少ないステップで処理できます。
3. 履歴のメモリが多いなら、不要になったチェックポイントを `drop` で捨てます（第11章）。
4. 実際のプログラムは、ステップ数やネイティブ処理量が、他の API の費用に比例することがあります。各 API の費用は、[libraries/README.md](../../libraries/README.md) と標準ライブラリの文書に書かれています。

処理が重くなる原因は、プログラムの書き方だけでなく、データの量や、チェックポイントに保持しているデータの量にもあります。「論理的な仕事量」を測るという考え方で、まず測り、それから直す、という順番で取り組んでください。
