# REWIND プログラミング言語設計案 v0.4

作成日: 2026-09-30  
状態: 実装済み設計の原案。v0.3 の実装を前提に、複数の処理を扱うプログラムの決定性と、ライブラリの配布・更新の安全性を定める。具体的な規則・使用方法・制限は [v0.4 実装仕様](v0.4-status.md) を参照する。

## 1. 目的と優先順位

v0.3 は単一の実行系列、仮想 I/O、Checkpoint、パッケージ設定を備える。v0.4 では次の順に拡張する。

1. `async`/`await` と決定的なタスクスケジューラ。
2. タスク間通信と取消し、Checkpoint に対する原子的なタスク集合。
3. パッケージの署名・権限宣言・再現可能ビルド。
4. デバッガ、性能計測、診断情報の改善。

v0.1〜v0.3 のソースと観測 Journal は互換性を保つ。新機能は明示的に選択した場合だけ有効にする。

## 2. 決定的な非同期実行

```rewind
async fn worker(input: String) -> Result<String,FileError> {
    return File.readText(input);
}

let a = spawn worker("a.txt");
let b = spawn worker("b.txt");
let first = await a;
let second = await b;
```

`async fn` は `Task<T>` を返す。`spawn` はタスクを VM に登録し、Host スレッドや OS の実行順序には依存しない。実行可能なタスクは作成順の ID と明示的な優先度で選ぶ。外部観測の完了順序も Journal に記録し、再実行時には記録された順序を使う。`await` は仮想 I/O とタスク完了でのみ中断できる。CPU を使い続けるタスクには v0.2 の命令予算を個別に適用する。

実時間のタイマー、ソケット、OS スレッドはこの版の標準 API には含めない。`sleep` を追加する場合は仮想時計のイベントとして定義し、Host 時計を直接読まない。

## 3. 通信、取消し、失敗

`Channel<T>` は容量を指定する FIFO キューとする。`send` と `receive` は `await` でき、同時に待機するタスクは ID 順に解放する。共有可変値は暗黙に許可せず、タスクに渡す値は所有権を移すか不変値として共有する。閉じたチャネル、取消し、タスク失敗は `Result` で返す。

`TaskGroup` を導入し、スコープを抜ける際に子タスクを待機・取消しする。親の `?` と panic では子を作成順の逆順で取消し、各タスクの `defer`/`using` cleanup を完了してからエラーを返す。タスク間の循環待機を検出したら、待機グラフを含む診断を返す。

Checkpoint はスケジューラの実行可能キュー、各タスクの PC・Frame・スタック、チャネル内容、待機関係、観測カーソルを一つの状態として保存する。`revert`/`resume` で一部のタスクだけを復元してはならない。`publish` は全タスクの仮想変更を統合した後に競合を検証する。

## 4. パッケージと効果の宣言

`rewind.toml` に依存パッケージの取得元、版範囲、必要な能力を宣言する。lockfile は正確な版、内容ハッシュ、署名主体、言語・コンパイラ版を記録する。`check` と `build` は lockfile に一致する内容だけを使い、実行時にネットワーク取得しない。依存更新は明示的な `rewind update` に限る。

ライブラリは `effects` で必要な仮想能力（ファイル読み取り、ファイル書き込み、環境値、引数、時計、乱数、タスク生成）を宣言する。呼び出し元が許可していない能力は `check` で拒否する。`publish` はライブラリから直接実行できず、アプリケーションの公開境界でのみ許可する。依存物の署名は配布元の識別に使うが、署名済みコードにも権限検査を適用する。

再現可能ビルドの検査では、同一ソース、lockfile、コンパイラ版、ビルド設定から同じ命令列と API 文書ハッシュを生成する。ビルド成果物には絶対パスや Host 時刻を含めない。

## 5. 開発体験

- `rewind debug`: Checkpoint とタスクの状態を読み取り専用で表示し、PC、Frame、捕捉 cell、仮想ファイル差分を追跡する。デバッグ操作自体は Journal を変更しない。
- `rewind replay TRACE`: 記録済み Journal と lockfile で実行し、最初の不一致箇所と必要な観測キーを示す。環境値は既定でマスクする。
- `rewind profile`: タスク別の命令数、ヒープ量、Checkpoint 共有量、Journal 消費量を出力する。計測はプログラムの仮想 stdout/stderr に混ぜない。
- `rewind test`: タスクのスケジュールを固定した試験に加え、許されたスケジュールを系統的に探索するモードを用意する。探索上限を Budget に指定する。

## 6. 完了条件

1. 同じソース・lockfile・Journal から、タスクの実行順と仮想出力が一致する。
2. `commit`、`revert`、`resume` が待機中のタスクとチャネル内容をまとめて復元する。
3. 取消し・`?`・panic・予算超過で cleanup が規定の順序で実行され、Host に未公開の変更が漏れない。
4. 依存物のハッシュまたは署名が変わった場合に実行前に拒否する。未許可の効果は静的に診断する。
5. 既存の v0.1〜v0.3 のテストとスクリプトがそのまま動く。

## 7. 対象外と検討事項

ネットワーク通信、データベース、FFI、子プロセス、GPU、任意のデバイス I/O は v0.4 の通常 API に含めない。これらは Journal の観測単位、再実行の安全性、`publish` の補償手順が個別に必要である。

原案の未決定事項は実装で次のように確定した: 優先度は `Task.setPriority(Int)`、信頼基点はアプリケーションの明示公開鍵、取得元はルート内の配置済みローカルミラー、探索は通常無効で `--explore N` の明示上限を使う。await は `Result<T,String>`、共有値は不変 snapshot、using TaskGroup の退出は取消し、正常な待合せは明示 join とした。

対話デバッガ、静的な転送可能性検査、配布して直接実行できる成果物はこの実装には含めず、[v0.5 提案](REWIND_v0.5.md) に記す。`build` は再現可能な命令テンプレートを生成し、`debug` は保存状態または仮想実行の状態を表示する。
