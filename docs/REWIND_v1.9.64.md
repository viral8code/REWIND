# REWIND v1.9.64 — 分割数値入力とサービスの同時実行

## 実装する単位

数値入力の準備と GUI・通信・DB の同時負荷をまとめて扱う。
`std.numericInputAsync.fromFloat` / `fromInt` は所有する List から数値配列へ
最大 4096 セルずつコピーし、各処理の間で scheduler へ制御を返す。
同期版の契約を維持し、float の raw bits と整数値を変更しない。
不正な形状・型・cursor はコピー前に検査し、取消時に部分配列を返さない。

List のページと配列の COW ページは通常の VM root / checkpoint 管理へ接続する。
古い checkpoint が保持する作業状態は残し、到達不能な一時値を回収する。
仕事量と scratch の admission は各分割処理の前に行う。
分割の追加費用を含む CPU / wall / RSS / live storage の比較は公開前の検証に残す。

`service-numeric` は入力生成、forward / backward、GUI の操作、HTTP request、
SQLite / PostgreSQL の transaction を同時実行する。
値と勾配を解析式で検算し、完了通知は容量 1 の Channel で渡す。
外部書込みと VM snapshot の境界は既存の `external` / `external fresh` のまま。

## 公開の受入

- 入力コピーの checkpoint 復元・取消・GC・source-free replay と旧言語版の拒否。
- 両 DB の反復負荷、部分失敗、通信切断、数値 task 取消と shutdown の資源解放。
- 同期版との最適化ビルド比較。長時間の応答性とメモリ増加の評価。
- 標準ライブラリ API baseline、reference、両 OS の展開後 SDK と全回帰。

公開は上記の受入、両OSの全回帰と署名付きSDKの展開後検証を条件とする。

## 開発中の確認結果

Linux の直接ビルドで、4097 セルの debug 記録と 16385 セルの compact 記録を
ソース削除後に実行し、入力コピーの途中 checkpoint への復元と replay を確認した。
64 / 256 回の取消試験では、到達可能な入力を残し、数値ページの増加を
基準値 + 4 MiB 未満、残る task / quota の件数を 64 未満として検査した。
旧言語版は新しい分割入力 primitive を拒否する。

最適化ビルドでは、SQLite / PostgreSQL 各 2 サイクルで実 GUI・HTTP・DB と
数値計算の完了、確定データの独立照合、資源解放、サービスなし replay を確認した。
SQLite 16 サイクルでは計算 10 回、GUI 操作 32 回、終了時の live 数値ページ 0、
外部資源 0 を確認した。この実行の native 入力標本は 0.011〜0.145 秒、
VM RSS は約 88.4〜89.7 MiB。ただし他の検証と同時実行した単一の標本であり、
長時間の上限や percentile を保証する測定ではない。

その compact 記録の replay は元の出力と一致したが、並行検証中の再測定で
約 203 秒を要した。長い再生の費用の切分けと改善は残件として保持する。
展開後 SDK、実 Windows、最終ソースの全回帰の完了へこれらの結果を広げない。

PostgreSQL 16 サイクルでも数値計算 10 回、GUI 操作 32 回、確定結果の独立照合、
サービスなし source-free replay、終了時の数値ページ / 外部資源 0 を確認した。
並行検証中の native 入力標本は 0.021〜0.507 秒、VM RSS は約 89.0〜90.0 MiB。
応答時間の変動と replay の費用は、負荷を分離した測定で引き続き確認する。

## 入力変換の比較

Linuxの最適化ビルドを使い、同じ非ゼロListの準備、入力変換、値の照合、
起動・profileを含めて、warmup後の3回を直列測定した。コンパイルは含まない。
`benchmark-numeric-input.py` で同じ手順を再実行できる。

| 262144要素 | wall中央値 | CPU中央値 | peak RSS中央値 | 終了時live数値storage |
| --- | ---: | ---: | ---: | ---: |
| 1.9.63同期 | 0.428秒 | 0.428秒 | 75236 KiB | 4951672 bytes |
| 1.9.64同期 | 0.432秒 | 0.432秒 | 75436 KiB | 4951672 bytes |
| 1.9.64分割 | 0.980秒 | 0.980秒 | 132376 KiB | 4951672 bytes |

分割版はこの標本で同期版の約2.27倍の時間と、約1.75倍のpeak RSSを使った。
分割による応答機会は追加費用を伴い、高速化や省メモリ化とは扱わない。
同期APIは必要な許可と型の契約を変更していない。

通常のサービス例は128要素・1回の有限計算とし、詳細記録の固定上限内で検証する。
反復試験は16384要素の連続計算とcompact記録を使う。入力値の一括準備は
per-cell VM loopの記録を避ける。応答前の接続切断とDB処理中のStopも、
確定結果の独立照合・外部資源の解放・サービスなしreplayで検証する。

短い実行は自動GCの開始閾値へ達しない場合があるため、即時の数値storage 0を
契約にはしない。有限128要素例は64 KiB以内、反復試験は4 MiB以内・残るtask64未満・
GC完了を検査し、外部資源はどちらも0を要求する。保持されたcheckpointと
観測の領域は、到達不能な一時値とは区別する。

## 一括入力準備を使う反復試験

入力の生成を一括処理へ変えた最適化ビルドで、他のビルド・試験を同時実行せず
両DB各16サイクルを確認した。SQLiteでは計算129回、GUI入力32回、実行29.49秒・
replay32.97秒、RSS94.08〜95.32 MB、入力標本0.011〜0.035秒。PostgreSQLでは
計算347回、GUI入力32回、実行67.16秒・replay88.67秒、RSS95.07〜95.98 MB、
入力標本0.013〜0.036秒だった。終了時のlive数値storageはそれぞれ約1.03 MiB・
0.52 MiB、外部資源は0で、自動GCの完了とtask件数の上限を確認した。

旧VMループによる入力生成の試験とは完了計算数と並行負荷が異なるため、
replayの速度比を保証する比較にはしない。反復試験の仕事量上限は5 billion×
サイクル数として明示する。通常の処理系の上限値を引き上げたものではない。
詳細記録の有限例、受理後切断、DB処理中のStopは別の検証として維持する。

子taskの失敗を `AutodiffTask` にまとめる既存ライブラリ経路は、元の原因コードが
隠れる制限としてv2の診断監査へ残す。これを改善済みとは扱わない。
