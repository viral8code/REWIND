# REWIND v0.4 実装仕様

更新日: 2026-09-30

実装版: Rust crate `0.4.0`。設計案の具体的な選択と、現在の利用範囲を以下に記す。

## 1. 非同期処理

```rewind
async fn twice(n: Int) -> Int { return n * 2; }
let task = spawn twice(21);
assert_eq(await task, Ok(42));
```

- `async fn` の呼び出しは、まだ実行を開始していない `Task<T>` を作成する。`spawn`、`await`、`TaskGroup.add` が開始する。通常の関数値としても呼び出せる。
- `await task` の型は `Result<T,String>`。取消しは `Err("TaskCancelled")`、閉じたチャネルは `Err("ChannelClosed")`。実行時エラーは位置と原因を含む String になる。T が Result の場合は二重の Result になる。
- 単一 VM 内の協調実行。待機または完了の際に、実行可能な関数タスクを `(優先度, 作成 ID)` の昇順で選ぶ。既定優先度は 0、`task.setPriority(Int)` で変更できる。CPU 処理への割込みや OS スレッドは使わない。
- `task.cancel()` は冷たいタスク・待機中タスクを取り消す。子を作成順の逆順で取り消し、登録済み cleanup を LIFO で実行する。実行中の自分自身の同期取消しは拒否する。
- `Channel<T>(capacity)` は FIFO。容量 0 は送受信の待合せ、最大容量は 65,536。`send(T)` は Task<Unit>、`receive()` は Task<T>。`close()` は残る値を受信可能にしたまま、新規送信を拒否し、空になった受信をエラーにする。待機操作は ID 順に処理する。
- `using group = TaskGroup(); group.add(task);` は開始と終了時の取消しを登録する。正常終了の待合せには `await group.join()` を明示する。スコープ退出は残るタスクを登録順の逆順で取り消す。
- エントリ終了時に、開始済みのタスクを最後まで実行する。未開始のタスクは実行しない。タスクの失敗を処理するには `await` または group.join の Result を調べる。
- 進めるタスクがないのに待機が残ると、タスク ID と待機状態を含む `TaskDeadlock` を返す。

### データと予算

引数、チャネルに送る値、戻り値は深い不変 snapshot にする。親のコレクションを後から変更しても子に反映しない。タスク作成時のグローバル値も独立した cell に保存し、子の var 代入は親へ反映しない。Task、Channel、TaskGroup は識別ハンドルとして共有する。

FileHandle、クロージャー、循環オブジェクトは転送できない。グローバルの関数シンボルは保存できるが、関数値の引数・戻り値・チャネル転送はこの版では拒否する。現在は全グローバルを保存するため、無関係なグローバル資源やクロージャーもタスク作成を妨げる。転送可能性と snapshot の変更禁止は実行時検査であり、所有権の静的型検査は v0.5 の提案対象である。

全体の命令予算は従来の `runtime { executionSteps = ...; }`、非同期タスクごとの上限は既定 100,000 命令（`--task-steps N`）。命令数は revert/resume でリセットしない。スケジューラのオブジェクトは計 4,096 個、保持状態と Checkpoint コピーの論理保存量は 16 MiB を上限にする。これは保守的な計算で、プロセス全体の使用メモリを表す値ではない。Runtime の historyMemory/historyStorage の制約も別途適用される。

## 2. Checkpoint と公開境界

`commit`、`revert`、`resume`、`branch` は、各タスクの PC・Frame・スタック、開始状態、優先度、待機関係、チャネルのキュー、グループ、ID 採番、グローバル cell を Runtime のヒープ・仮想 I/O・観測カーソルとまとめて復元する。`branch` を抜けると、分岐内で作成したタスクも破棄する。

revert の継続 Frame 検査は v0.3 と同じ。別タスクからの復元や終了済み Frame の復元には resume を使う。Budget と開発ツールの命令履歴は累積し、復元で消さない。

`publish` はアプリケーションタスクのみが実行でき、開始済みの子がすべて完了・取消し済みであることを要求する。ライブラリと async 関数からの直接・間接の publish は拒否する。公開の競合検査と部分失敗の扱いは v0.1 と同じ。

## 3. v0.4 プロジェクトと署名

`rewind.toml` の例:

```toml
language = "0.4"
source_root = "src"
entry = "main.rw"
effects = "fileRead,output,tasks"

[dependencies]
math = "file:vendor/math"
[dependency_versions]
math = "^1.2.0"
[dependency_signers]
math = "author"
[trust]
author = "<64桁の Ed25519 公開鍵の16進表現>"
```

`vendor/math/rewind.package.json`:

```json
{"name":"math","version":"1.2.3","effects":[]}
```

署名と更新:

```sh
rewind sign vendor/math --key /private/author.seed
rewind update --root .
rewind check --root .
rewind build --root . --output rewind.build.json
```

- seed ファイルは 32 byte の秘密 seed を 64 桁の16進文字列にしたもの。sign は公開鍵だけを標準出力へ返し、パッケージ直下の `rewind.signature` に署名を保存する。鍵の生成・保管・配布は利用者が管理し、秘密鍵をリポジトリへ入れない。
- SHA-256 の入力は、パッケージ下の全 `.rw` と `rewind.package.json` の相対パス・内容。順序を固定し、長さを付けて連結する。署名メッセージは `REWIND-PACKAGE-v1\n` と内容ハッシュ。Ed25519 の strict 検証を使う。
- 信頼基点はアプリケーション manifest の公開鍵。依存側の鍵で置換できない。パッケージ名、SemVer の版範囲、効果、署名を検証する。シンボリックリンクとルート外の依存を拒否する。
- 取得元はルート内に事前配置したローカルミラーのみ。update は配置済みの版を検証して固定する操作で、リモートからの取得や最新候補の探索はしない。依存パッケージのさらに先の依存もアプリケーション側で明示する。
- lockfile format 2 は正確な版、SHA-256、署名・署名主体・公開鍵、相対取得元、アプリケーションの権限、言語・コンパイラ版を固定する。check/run/build/doc は一致を要求し、自動更新しない。依存がない v0.4 プロジェクトも最初に update が必要。v0.2/v0.3 の lock の規則は維持する。

### 効果の検査

ライブラリは先頭に `effects {fileRead, output, tasks}` のように宣言する。効果は `fileRead`, `fileWrite`, `output`, `input`, `clock`, `random`, `env`, `args`, `locale`, `tasks`。未知の効果を拒否する。

直接操作と呼び出し先の必要能力を保守的に集め、モジュール宣言、パッケージ metadata、アプリケーション manifest の許可内か検査する。未使用関数も検査対象であり、同名の impl メソッドは保守的にまとめる。Task/Channel を含むシグネチャも tasks 能力を要求する。Env の名前ごとの `--allow-env` / `--secret-env` は別途必要。

## 4. ビルド・記録・検査

```sh
rewind run examples/v04.rw --root . --record session.json
rewind replay session.json --root .
rewind debug session.json
rewind debug examples/v04.rw --root . --record debug.json
rewind profile examples/v04.rw --root .
rewind test tests.rw --root . --explore 100
```

`build` はソースを実行せず、命令テンプレート、シグネチャ、ソース・lockfile・API 文書のハッシュを整列した JSON に出力する。同じ入力から同じ byte 列を生成し、異なる配置ルートでも一致する。絶対パスや作成時刻を含まない。generic の単相化は従来通り初回実行時に行う。この JSON を直接実行するローダーはまだ提供しない。

`run --record` は成功した実行の外部観測、命令順、タスク ID、最終状態ハッシュ、Checkpoint の検査状態、タスク予算を記録する。`replay` は現在のソース・lockfile・コンパイラ版を照合し、観測を記録から読み、最初の命令順・観測キー・最終状態の不一致を報告する。Host ファイルは書き換えない。通常記録の仮想公開は標準出力・標準エラーへ再生する。記録・読込みファイルの上限は 128 MiB。

`--secret-env` の値を記録から除き、検査表示の既知の値を `<redacted>` に置換する。再生にも同じ名前の `--secret-env` と値の供給が必要。通常の環境観測・入力・観測ファイルは再生用に保存される。記録は暗号化・署名されておらず、プログラムが秘密値を変形して別の観測へ書くことまでは自動追跡しない。

`debug TRACE.json` は保存済み状態の読取り専用表示。`debug FILE.rw` は仮想実行し、publish を仮想状態に留めて実ファイルと出力ストリームへの公開を抑止する。後者は初回の Host 読取りを行う。表示するのは Checkpoint、PC、Frame、cell を含むヒープ、仮想ファイルの変更パス、タスク状態、キュー数、観測カーソル。対話的な一命令ずつの操作やファイル差分本文表示は未提供。

`profile` はタスク別命令数、論理ヒープ量、Checkpoint のヒープ root 共有数、観測ファイル量、出力 Journal 量、スケジューラ保存量を stderr に出す。RSS や実時間の性能測定ではない。profile の通常実行では、ソースの publish は実際に公開する。

`test --explore N` は同じ優先度の実行可能タスクの選択肢を幅優先で探索する。N は各テストの実行数上限（1〜10,000）、既定は通常の決定的実行のみ。候補の残数を報告し、残る場合は網羅したとは扱わない。各実行は独立した Runtime と観測を使う。環境・時計などが変化するテストでは、スケジュールだけが違う試験とはならないため、固定データの純粋・仮想処理を使う。失敗時は選択系列を表示する。

## 5. 検証と次版

v0.4 統合テストは決定順序、優先度、関数値、データ分離、容量 0/1 の通信、取消し cleanup、タスク予算、待機中の resume、revert、branch、デッドロック、署名改変、効果検査、配置場所を変えた再現可能ビルド、記録再生、不一致、秘密値マスク、デバッグの仮想公開、スケジュール探索を検証する。既存の v0.1〜v0.3 テストも維持する。

所有権型、型付き TaskError、関数ごとの効果、実行可能な成果物、対話型デバッガと診断の拡充は [v0.5 提案](REWIND_v0.5.md) に記す。
