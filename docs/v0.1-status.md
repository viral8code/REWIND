# v0.1 runtime status and consistency decisions

The Rust runtime implements the transactional resources listed in [REWIND_v0.1.md](REWIND_v0.1.md): compute state, heap, stack, globals, files, directories, stdin, stdout, stderr, clock, and random. This document records the v0.1 decisions. The v0.2 language implementation is described in the repository README.

## Verified behavior

- `commit` creates a named, shared-root state snapshot without publishing host effects. `revert`, `branch`, and `drop` manage the state graph. Compute roots include globals, locals, heap objects, stack, call frames, program counter, counters, and random state.
- Output and file changes remain virtual until `publish`. Input and clock observations remain outside snapshots; their cursors rewind and replay. A strict file snapshot freezes contents, while ordinary file handles cache blocks on demand.
- Files use shared 4 KiB pages. Output journals, virtual file pages, strict snapshots, and observed host blocks can spill to temporary storage. Configurable budgets bound these segments and estimated compute payloads.
- `publish` checks observed file content fingerprints and directory entries, stages replacement files, applies filesystem changes, then outputs stdout and stderr. A partial failure reports applied resources and prevents automatic retry. Multi-resource publication is not globally atomic, as the specification allows.

## Interpretations needed to make v0.1 consistent

1. **Host conflict baseline.** Section 31 describes changes since checkpoint creation, but section 45 requires near-constant-time `commit`. Capturing every possible host path at every checkpoint would violate that goal. The runtime tracks a host path from its **first observation in the current file epoch**. A change before first observation cannot be detected as a conflict. The original specification should state this boundary explicitly.
2. **Input example.** Section 38 suggests `In.readLine()` after `revert answered` replays the previously read line. Sections 11–12 define the cursor unambiguously: if checkpoint `answered` was created after a read, the next read consumes the following journal entry. To replay that line, checkpoint before reading it. The implementation follows sections 11–12.
3. **Program counter after `revert`.** The Rust API restores the saved counter. In the v0.1 example interpreter, execution continues after the `revert` statement. The v0.2 VM implements this behavior and adds `resume` to continue at the saved counter.
4. **Unsupported external resources.** Network sockets, databases, child processes, shared memory, GPU, device I/O, and native handles are prohibited in the v0.1 language surface. The optional `unsafe external` provider is not supplied.

## Operational limits

- File open and uncached block validation scan a 128-bit content fingerprint. This detects same-size, same-timestamp edits, but hashing is not a cryptographic security boundary.
- Cross-file and terminal atomicity is unavailable. If publication partially applies, inspect the reported host resources before starting a new runtime.
- The history budget is an estimate for compute values and tracked segments. Input/time logs, metadata structures, and transient allocations are outside the configured budget.
- General functions, conditionals, loops, modules, and the type system belong to the v0.2 language layer. They are available through `rewind run` and `rewind check`.
